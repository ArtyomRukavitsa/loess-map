# Деплой обработчика публикаций (fn_process) — вместо ВМ

Эта функция делает то же, что локальный `57_process_uploads.py`: распознаёт загруженный файл,
извлекает разрезы, привязывает фразы к страницам, геокодирует и складывает предложения на проверку.
После её появления **ноутбук для обработки загрузок больше не нужен**.

## 1. Создать функцию

| Параметр | Значение |
|---|---|
| Имя | `fn-process` |
| Среда выполнения | **`python311`** |
| Точка входа | **`index.handler`** |
| Память | **2048 МБ** (рендер страниц PDF) |
| Таймаут | **3600 с** |
| Файлы | `index.py`, `requirements.txt` из этой папки |

Таймаут больше 10 минут делает функцию «долгоживущей» — отдельно ничего включать не нужно,
просто поставь значение. Сервис вправе остановить такой экземпляр досрочно, поэтому обработка
написана **возобновляемой**: распознанные страницы сохраняются кусками, следующий запуск продолжает
с места остановки.

## 2. Переменные окружения

| Переменная | Значение |
|---|---|
| `YC_FOLDER_ID` | `<идентификатор каталога — см. .secrets>` |
| `YC_API_KEY` | из `.secrets` (`YANDEX_API_KEY`) |
| `BUCKET` | `loess-results` |
| `AWS_ACCESS_KEY_ID` | из `.secrets` |
| `AWS_SECRET_ACCESS_KEY` | из `.secrets` |

Необязательные: `MODELS` (по умолчанию `deepseek-v32:3,qwen3.6-35b-a3b:1`), `CHUNK` (40 страниц за
раз), `MAX_PAGES` (400), `TIME_BUDGET` (2400 с — после этого функция сохраняется и выходит).

## 3. Триггеры — здесь главная осторожность

### 3.1 Триггер на загрузку файла (быстрый старт)

Тип **Object Storage**, бакет `loess-results`, событие **«Создание объекта»**,
префикс `uploads/`, **суффикс `.pdf`**.

> ⚠️ **Суффикс обязателен.** Без него триггер сработает и на `status.json`, который функция
> сама же перезаписывает по ходу работы, — получится бесконечный цикл вызовов.

### 3.2 Триггер по таймеру (страховка)

Тип **Таймер**, cron `0/10 * * * ? *` (раз в 10 минут). Без аргументов функция сама находит все
задачи со статусом `queued` и дообрабатывает прерванные.

Этот триггер закрывает три случая: загрузку картинок (не `.pdf`), досрочную остановку
долгоживущего экземпляра и любой сбой первого триггера.

Одну и ту же задачу два запуска не возьмут: как только обработка началась, статус меняется на
`processing`, а по таймеру подбираются только `queued`.

## 4. Проверка

```bash
# ручной запуск конкретной задачи
curl -X POST "https://functions.yandexcloud.net/<ID>" \
  -H "Content-Type: application/json" -d '{"job_id":"<job_id>"}'

# запуск разбора очереди (как по таймеру)
curl -X POST "https://functions.yandexcloud.net/<ID>" -H "Content-Type: application/json" -d '{}'
```

Затем загрузи PDF через `upload.html` и следи за статусом на самой странице:
`в очереди → распознавание N–M из K → извлекаю данные → готово`.

Публичный доступ этой функции **не нужен** — её вызывают триггеры, а не браузер.

## 5. Что остаётся локальным

Перенос **принятых** объектов на карту (`61_publish.py`) сознательно оставлен командой на машине:
он пересобирает и публикует карту заказчика, и это должно быть осознанным действием.
В облако его выносить смысла мало — шаги привязки страниц и рендера сканов полнокорпусные,
и функция каждый раз перемалывала бы весь архив ради нескольких новых точек.
